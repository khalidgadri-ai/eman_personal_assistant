# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository overview

This repo contains one app, built with **Flutter** (`lib/`, `pubspec.yaml`; targets Android/iOS/Web/Windows/Linux/macOS): "إيمان" / eman, a personal life/home assistant (tasks, health, kitchen/pantry, finance, and an AI assistant that works with the user's own provider key: Gemini, Claude, or any OpenAI-compatible service). The old vanilla JS PWA (`app.js`, `index.html`, `styles.css`, `manifest.json` at the root and their `web_app/` copies) was removed on 2026-11-05: it put the Gemini key in the request URL, used shut-down models and carried one person's sample data. Do not bring it back; the web build is `flutter build web` from `web/`.

There is also `agent_engine/` — only compiled `__pycache__/*.pyc` artifacts are present, no source `.py` files exist in the repo currently.

## Commands

Flutter app:
```
flutter pub get              # install dependencies
flutter run                  # run on a connected device/emulator
flutter run -d chrome        # run the web build
flutter run -d windows       # run the Windows desktop build
flutter build apk            # build Android APK
flutter build web            # build web (outputs to build/web)
flutter analyze              # static analysis (flutter_lints)
flutter test                 # run all tests
flutter test test/widget_test.dart   # run a single test file
```

## Architecture

### Flutter app (`lib/`)

- `main.dart` — app entry point; calls `Hive.initFlutter()` before `runApp`. `EmanLifeApp` opens `AppGate`: on first run it shows `OnboardingScreen` (`features/onboarding/`: name → interests + goals, saved in the encrypted `profile` box) until a profile exists, then `MainNavigationScreen`; the gate re-checks when `AppEvents.dataErased` fires (after "مسح كل بياناتي"). `MainNavigationScreen` is a single `StatefulWidget` holding all five feature screens in an `IndexedStack`, switched via `BottomNavigationBar`, plus two floating buttons (life coach, feedback). There is no router and no external state-management package (no Provider/Riverpod/Bloc) — each feature screen manages its own local state.
- `core/ai/` — the provider-neutral AI layer; **no model name is pinned in the calls**. `AiProvider` (`ai_provider.dart`) is the abstract class; three adapters in `adapters/` talk to the providers over plain `http` (no vendor SDK): `OpenAiCompatibleProvider` (OpenAI, xAI, OpenRouter, Groq, DeepSeek, Mistral, any custom https server: `{base}/chat/completions`, `{base}/models`), `AnthropicProvider` (`/v1/messages`) and `GeminiProvider` (`generateContent`, key in the `x-goog-api-key` header never in the URL). `provider_presets.dart` lists base URLs and key-creation links only, never model names; the user types the model or fetches it with "جلب الموديلات المتاحة". Verify preset URLs and each adapter's request shape against the provider's official reference before a release; `test/ai_adapters_test.dart` pins them with `MockClient` fixtures that are hand-built from those references (live checking needs the user's own key, via the in-app "اختبار الاتصال").
  - `core/config/ai_config.dart` — `AIConfig.modelName` is only the *starting suggestion* for the Gemini preset, and that literal must stay in this one file (a test fails otherwise). Verify any new name against ai.google.dev/gemini-api/docs/models and /deprecations, never guess: `gemini-2.0-flash` was shut down on 2026-06-01.
  - `AiService` (`ai_service.dart`) is what screens use; each AI-powered feature (exercise-image analysis, recipe suggestions, voice-note-to-tasks parsing, medication-label analysis, budget category limits) is one method on it that builds an Arabic prompt and calls `askAssistant()` or `analyzeImage()`. New AI features follow this one-method-per-capability pattern (the life coach is the one deliberate exception: it calls `sendRaw()` because it needs a real system prompt and must see provider errors).
  - `AiService.create({systemPrompt})` is the only production constructor (`withProvider` exists for tests). If no provider+key is saved `isConfigured` is false and `askAssistant`/`analyzeImage` return `missingKeyMessage` instead of calling anything. A model marked "does not support images" is never sent one (the user is told instead); "unknown" is tried and a refusal is explained.
  - Screens get a service at the moment of use via `requireAiService(context)` in `core/widgets/ai_provider_screen.dart`, which shows the provider screen when nothing is configured and returns null if the user leaves without saving.
  - `resetModel(newKey)` saves a user-entered key for the selected provider (Gemini if none chosen) and re-initialises the provider — this is how a user activates AI features; preserve it as public API when refactoring `AiService`.
  - **Keys:** one per provider in `flutter_secure_storage` (`ai_key_<providerId>`), managed by `AiSettingsService` (`ai_settings_service.dart`); the non-secret config (provider, base URL, model, image support) is one JSON string `ai_config` in SharedPreferences. Keys never go in URLs, logs, the backup file or SharedPreferences (the old `gemini_api_key` pref is migrated once and removed). Only `https://` base URLs are accepted (Android blocks cleartext and v1 does not support local http servers such as Ollama).
  - Every failure becomes a fixed Arabic message from `AiFailure` (`ai_errors.dart`): users never see the provider's raw text, and logs print only the failure kind or exception type, never a body or key. Classification is by HTTP status first, then bounded matching on the provider's `error.message/type/status` fields.
  - The coach's `CoachAiService` and the settings tile both go through this layer; `google_generative_ai` is gone (a test fails if it comes back).
  - The general assistant's system prompt is `buildAssistantSystemPrompt(profile)` (`assistant_prompt.dart`): it is built only from what the user typed in onboarding and carries no pre-written personal data.
- `features/coach/` — the life coach ("مدرب يسأل"): a local question bank (`assets/coach_questions.json`), sessions stored in an encrypted Hive box (`coach_sessions`, see `encrypted_boxes.dart` below), and `CoachAiService` for optional AI follow-up questions. `CoachAiService` calls `AiService.sendRaw()` instead of `askAssistant()` because it needs a real system prompt and must see provider errors (`askAssistant` returns error text as a normal reply). Safety rules: `containsCrisisSignals()` runs before anything is sent to the model; a model reply containing `CRISIS_DETECTED` routes to the helpline dialog; replies with advice language (`containsAdviceLanguage()`) are replaced by a bank question. The coach's opening domain is a weighted random pick (`CoachSessionService.pickDomain`) boosted by `CoachSignalService`, which reads only on-device data (recent unplanned expenses, a topic repeated in the last two coach answers, more than two hours of social-app use today).
- `core/services/database_service.dart` — thin wrapper around `SharedPreferences` (the coach's session log and the expense log live in Hive instead), used as a simple key/value store (not a real database). Each domain (`daily_tasks`, `goals`, `pantry`, `recipes`, `shopping`, `laundry_schedule`, `quran_page`) is a single JSON-encoded string under its own key. **There is no default/seed data: a fresh install is empty** (`test/first_run_empty_test.dart` scans `lib/` for the old personal seeds and for wording addressed to one gender); a missing or corrupt value reads as an empty list. Follow this same get/save-as-JSON-string pattern for new persisted domains.
- `core/services/encrypted_boxes.dart` — `EncryptedBoxes.open(name)` opens the sensitive Hive boxes (`coach_sessions`, `expenses`, `budget_plan`, `profile`, `health`, `exercise_images`) encrypted with AES-256. The random key is generated once and kept in `flutter_secure_storage` (Android Keystore), never next to the data. The encrypted file is `<name>_enc.hive`; a leftover plain `<name>.hive` is copied into it and then deleted. Never open a plain box with a cipher: Hive treats it as corrupt and silently truncates it. Every new encrypted box must also be added to `res/xml/backup_rules.xml`, `data_extraction_rules.xml` (cloud-backup and device-transfer), `DataResetService.userBoxes` and `BackupService.boxNames` (a test checks the last two agree). Tests that use a Hive-backed service inside `testWidgets` must create it under `tester.runAsync` (real file/asset I/O hangs under the fake clock; `CoachSessionService` reads an asset). Tests use `test/helpers/test_storage.dart`: `TestStorage.create()` (real files) in plain `test`s, and `TestStorage.inMemory()` inside `testWidgets`, where real file I/O would hang.
- `features/budget/` — manual expense tracking: `BudgetService` stores entries in an encrypted Hive box (`expenses`); `BudgetSummaryScreen` (opened from the budget tab's app bar) shows the monthly total and a per-category `fl_chart` column chart. **Manual entry only, no exceptions:** never add bank linking, card numbers, Open Banking, or any external financial API.
  - **Budget plan** (the budget tab, `features/financial/financial_screen.dart`): `BudgetPlanService` keeps one `BudgetPlan` record (income, payday, currency, fixed expenses with a per-cycle "paid" mark, savings goal as amount or percent, optional category limits) in its own encrypted box `budget_plan` (`budget_plan_enc.hive`; listed in `res/xml/backup_rules.xml`, `data_extraction_rules.xml` ×2, `DataResetService.userBoxes`, `BackupService.boxNames`, and `TestStorage`). Nothing the user types on the tab lives only in a `TextEditingController`: the editor (`BudgetPlanScreen`) validates, saves on "حفظ الخطة" and asks before discarding unsaved edits. All figures are local pure functions in `budget_calculator.dart` (no AI): the cycle starts on payday (a payday of 29–31 clamps to the month's last day), available = income − fixed − savings, remaining = available − spent in the cycle, daily = remaining ÷ days left including today. "Paid" stores the cycle key (start date), so a new cycle clears it without any cleanup job. Amounts go through `parseAmount` (Arabic-Indic digits and `٫`; plain decimals only).
  - **Budget suggestion** (`BudgetSuggestionScreen`): the local rule (`defaultLimitWeights`) always works offline. The AI variant is optional and `AiService.suggestBudgetLimits` is only called after an explicit consent dialog **every time**, listing exactly the four numbers sent (income, fixed total, savings, available) and the provider; fixed-expense names and recorded expenses are never sent. The reply is untrusted JSON (`BudgetSuggestion.tryParse`) and only becomes category limits when the user taps "حفظ كحدود للفئات". The currency symbol in the expense screens follows the plan's currency.
- `features/awareness/` — "وعي الاستخدام" (Android only): today's minutes in five social apps via the system Usage Access permission (`PACKAGE_USAGE_STATS`, which the user enables manually in Settings), through the `usage_stats` package. Minutes are computed from raw `queryEvents` since local midnight (`foregroundTimeByPackage`), not `queryAndAggregateUsageStats`, whose daily buckets don't start at midnight. Only one number per app is stored (Hive box `app_usage`, today's snapshot only). **Never add** account logins, embedded social browsers, notification/message reading, `QUERY_ALL_PACKAGES`, or any upload of this data; the five package names are listed in both `models/social_app.dart` and the manifest's `<queries>`. `usage_stats` is pinned to 1.x because 2.x needs Flutter ≥ 3.44; 1.3.1's Gradle file uses `jcenter()`, which breaks on Gradle 9.
- `core/services/subscription_service.dart` — Google Play Billing (`in_app_purchase`), one auto-renewing product `eman_coach_monthly`. The **only** paid feature is the coach's AI follow-up ("عمّق أكثر", gated in `CoachScreen` via `CoachPaywallScreen`); everything else stays free. Status is cached in a Hive box (`subscription`) and trusted offline for `offlineGrace` (3 days); Google Play's `restorePurchases()` result is the source of truth, and purchases must be acknowledged (`completePurchase`) or Play refunds them after 3 days. Verification is client-side only (no server). Billing is Android-only; elsewhere `canPurchase` is false.
- `core/services/notification_service.dart` + `features/reminders/reminder_service.dart` — local reminders for medications, care-routine items and tasks (each has an optional `HH:mm` reminder set through the `isTime` field of `showEntryDialog`). `ReminderPlanner` turns the data into `PlannedReminder`s (pure, tested); `ReminderService.syncAll()` cancels everything and re-schedules from the current data, and runs at app start, after every change, after a backup restore; `cancelAll()` runs on "مسح كل بياناتي". Medication/routine reminders repeat daily, a task reminder fires once and is skipped when the task is done. They are **inexact on purpose** (`AndroidScheduleMode.inexactAllowWhileIdle`): never add `SCHEDULE_EXACT_ALARM`/`USE_EXACT_ALARM`. The manifest adds `RECEIVE_BOOT_COMPLETED` and the plugin's two receivers so reminders survive a reboot. No time-zone database is loaded: `NotificationService.locationFor` builds a fixed-offset location from the device offset (re-synced on every start, so a DST change is fixed at the next launch). Notification permission is requested only right after the user sets a reminder. All platform calls swallow errors by design.
- `features/<feature>/` — one screen per bottom-nav tab (`goals_and_tasks`, `health_and_fitness`, `kitchen_and_home`, `financial`, `ai_assistant`). Screens talk directly to `AiService`/`DatabaseService`; there is no repository/domain layer in between. `health_and_fitness/health_service.dart` keeps medications and the care routine in the encrypted `health` box. `features/settings/` holds `SettingsScreen` (profile edit, AI provider, encrypted backup, "مسح كل بياناتي") and `DataResetService`, which deletes the user boxes (never `subscription`), clears SharedPreferences and secure storage, and resets the service singletons. List-style screens add and edit items through the shared `showEntryDialog` (`core/widgets/entry_dialog.dart`; `EntryField.initial` pre-fills for editing, `isTime` adds an optional time picker). Deleting a list item shows an undo snackbar (`core/widgets/undo_snackbar.dart`) instead of a confirm dialog, except recipes/exercises deleted from their details page, which ask first.
- `features/settings/backup_service.dart` — the user's own encrypted backup file (`.emanbak`), the only way data moves to a new phone (Auto Backup excludes the encrypted boxes). AES-256-GCM, key from PBKDF2-HMAC-SHA256 (600k iterations, run through `compute`), the whole header is the GCM AAD, and the password is never stored (no recovery). It covers all the encrypted user boxes (`BackupService.boxNames`, including the budget plan) plus `DatabaseService.backupListKeys`/`quran_page`; the Gemini key, subscription cache and `app_usage` are left out on purpose. Restore decrypts and validates everything before writing, replaces (never merges), rolls back if a write fails, then bumps `AppEvents.dataRestored` so `AppGate` rebuilds the screens. File access goes through `BackupFileGateway` (`file_picker`, system Storage Access Framework, no storage permission). A new persisted domain must be added to `DatabaseService.backupListKeys` (or to a backed-up box) or it silently misses the backup. Tests: `backup_service_test.dart`, `settings_backup_test.dart`.
- `features/kitchen_and_home/` — `KitchenStore` (a `ChangeNotifier`) holds recipes, pantry/home supplies, the shopping list and laundry; the four tab widgets (`recipes_tab`, `pantry_tab`, `shopping_tab`, `laundry_tab`) all read it, so moving an item between tabs shows at once. Every item has a stable `id` (older data without ids gets them on first read and is saved). Recipes have structured ingredients (`RecipeIngredient`: name, amount, unit), steps, servings (`Recipe.scaledTo` rescales numeric amounts, "to taste" stays), pin; old free-text recipes still read (`ingredientsText`) and can be converted in the edit screen. `core/utils/quantity.dart` parses/format amounts (fractions, Arabic-Indic digits) and `core/utils/arabic_text.dart` compares Arabic names loosely (pantry-has / shopping merge). Adding a recipe's ingredients to shopping merges equal names and sums equal units.
- `features/health_and_fitness/` — `HealthService` keeps medications, care-routine items, **exercises** and the **workout log** in the encrypted `health` box (record `kind` field) and exercise photos in the encrypted `exercise_images` box keyed by exercise id. The AI exercise analysis asks for JSON; `ExerciseDraft.tryParse` treats it as untrusted data (type checks, clamps, control characters stripped) and only pre-fills the edit form: nothing is saved until the user presses save. Deleting an exercise keeps its workout history (entries carry the exercise name).
- `features/budget/` also supports editing and deleting a single expense (`BudgetService.updateExpense/deleteExpense/restoreExpense`); the monthly screen lists each expense.
- `features/coach/` sessions have an `id` (the box key) so a single session can be deleted from the history screen.
- The "تواصل معنا" button (`core/services/contact_service.dart`, `url_launcher`) opens the mail app to `AppContact.supportEmail` (`core/config/app_contact.dart`). **That constant must be set to the public support address before release; while it is empty the button is hidden.** The old developer-notes button and its `feedback_entries` storage are gone (the leftover pref is removed on first start).
- All user-facing strings and prompts sent to the AI provider are in Arabic; identifiers (files, classes, variables) are in English using standard Dart naming (snake_case files, camelCase members). Keep this split when adding code.

## API keys — no central key, by design

There is no central or fallback API key anywhere in the app. Every user activates AI features with their own key from the provider they choose, stored only on their device in secure storage (`AiSettingsService`). Do not add a shared key in any form — hardcoded, a bundled `.env` asset, or any other file shipped in the build — because anything bundled in a mobile or web app can be extracted. The old hardcoded key in the initial commit's git history must be treated as compromised.

## Android release

- `applicationId` (and `namespace`, and the Kotlin package of `MainActivity`) is `com.khalidibrahimgadri.eman` and cannot change after the first Google Play upload. iOS/macOS/Linux still carry the old `com.lifeapp.*` identifiers (iOS is deferred); the Dart package name stays `eman_life_app`. Bump the `+build` number in `version:` (pubspec) for every upload.
- Signing: `android/app/build.gradle.kts` reads `android/key.properties` (gitignored), which points to the upload keystore kept **outside the repo**: `%USERPROFILE%\keystores\eman-upload-key.jks`, alias `eman-upload` (PKCS12, so `keyPassword` equals `storePassword`; certificate `CN` is the owner's name). The owner created it personally on 2026-10-21 and keeps the passwords only in their password manager and backup copies of the file elsewhere; Claude never sees the passwords. The older `eman-release-key.jks` (alias `eman`, `CN=Eman Life App`, created 2026-10-04 by an earlier session) was never used for an upload and is superseded: do not sign with it. Play App Signing should stay enabled so this key is only an upload key. Without `key.properties`, release builds fall back to debug signing so `flutter run --release` still works; Google Play rejects debug-signed bundles.
- Release build: `flutter build appbundle --release --obfuscate --split-debug-info=build/symbols`. R8 minify + resource shrinking are on (`proguard-rules.pro`, `res/raw/keep.xml` keeps the notification icon); keep `build/symbols` per released version outside the repo to read crash stack traces. `targetSdk`/`minSdk` come from the Flutter SDK (currently 36/24); verify them in `build/app/intermediates/merged_manifests/release/.../AndroidManifest.xml`. `android/gradle.properties` pins the Gradle JVM to `-Duser.language=en`: on an Arabic-locale Windows, bundletool otherwise looks for `classes٢.dex` and `bundleRelease` fails at `packageReleaseBundle`.
- Permissions: the manifest declares only `INTERNET` (the chosen AI provider, billing), `PACKAGE_USAGE_STATS` (usage awareness) and `RECEIVE_BOOT_COMPLETED` (reminders survive a reboot, plus the plugin's two receivers); plugins add `POST_NOTIFICATIONS` and `VIBRATE` (flutter_local_notifications), `ACCESS_NETWORK_STATE` and `com.android.vending.BILLING` (Play Billing). `<queries>` declares the five social apps, `PROCESS_TEXT` and `SENDTO mailto`. `docs/play_data_safety.md` is the Data safety inventory; update it when a feature starts sending something new off the device. Do not add `CAMERA`, `READ_MEDIA_IMAGES`, `READ_EXTERNAL_STORAGE` or `RECORD_AUDIO`: `image_picker` works without them, and `READ_MEDIA_IMAGES` triggers Play's photo/video declaration. `test/security_config_test.dart` pins this permission list, the backup exclusions, and checks that no key-like string is in any shipped file (`lib`, `assets`, `android/app/src`, `web`).
- Backup: `res/xml/backup_rules.xml` (Android 6–11) and `data_extraction_rules.xml` (12+) exclude the encrypted Hive files and flutter_secure_storage's prefs (`FlutterSecureStorage.xml`, `FlutterSecureKeyStorage.xml`) from Auto Backup and device transfer, because the Keystore key can't be restored on a new phone. Add any new encrypted box to both files.
- Launcher icons are generated from `eman_logo.png` by `flutter_launcher_icons` (config in `pubspec.yaml`): run `dart run flutter_launcher_icons` instead of editing the `mipmap-*`/`drawable-*` icons by hand. The app's on-device name is `android:label="إيمان"`, which the usage-awareness steps also reference.

## Files not to modify without explicit confirmation

- `pubspec.lock` — regenerate via `flutter pub get`, don't hand-edit.
- Any `.env` file, if/when one is introduced — never print its contents in a response or commit.
- `android/key.properties` and the upload keystore — never print, commit, move into the repo, or regenerate them (after the first upload, a new upload key needs a reset request in Play Console).
- `resetModel()` in `core/ai/ai_service.dart` — this is how a user saves their own API key; preserve it as public API when refactoring `AiService`.
